## 继承的测试结论

上一段开发记录已经验证过 Codex／Obsidian／Claude 单次插入且不发送、当时的不支持目标回退与剪贴板保留、连续录音及会话内密钥复用，以及文字整理样本测试。保留这些结论和对应版本／场景，不标记成从未测试，也不据此宣称所有后续构建均已实测。

特别注意：旧版“处理期间停留 Mini Typeless 时不插入”与新版“返回原目标后检查插入”行为不同，旧结论是基准，不能直接当作新版恢复逻辑通过。

## 建议顺序

1. 开发侧先完成异常分支自动化（本轮已补齐上述取消与迟到响应场景）。
2. 补一次十分钟真实到期录音，同时覆盖突破旧上限、跨分段和最终自动处理；可以在处理期间切回 Mini Typeless，顺带观察返回目标行为，避免多轮重复验收。
3. 将实际观察记为通过或待查。目标恢复目前没有已确认故障；正常使用中若再次出现明确问题，先收集完整记录，再调试，不根据已撤回的模糊印象改代码。
4. 固定代码版本与验收记录，进入职责拆分。每批行为保持不变，独立验证并记录；如发现功能缺陷，单独说明修复范围。

## 拆职责如何落实成拆文件

以下是计划中的模块名，不表示已经实现：

- 第一批 `InsertionCoordinator.swift`：持有插入检查生命周期、恢复目标和粘贴流程；通过接口调用焦点查询／系统粘贴，通过回调报告状态。窗口负责显示，不直接推进粘贴。回归：恢复原目标、第三应用切换、取消／重复操作、兼容模式条件、一次粘贴与剪贴板恢复。
- 第二批 `UsageStore.swift`：用量累计、序列化和读取；沿用既有存储键与格式。回归：跨片段统计不重复、旧数据可读、合成测试不写用户统计。
- 第三批 `MainWindowController.swift`：界面和按钮状态；业务流程通过明确事件连接。回归：窗口布局、按钮可用状态，以及停止录音到结果的集成链路。
- 钥匙串服务若继续拆分，单独作为最后一批小改动，保留服务名、账户、签名和 entitlement。先验证调用参数与取消行为，避免为纯重构反复触碰真实密钥。

不会仅把一个大类机械拆成多个 extension 文件；目标是让每个模块只管理自己的状态，降低其他模块直接修改它的机会。

## “相关回归”的含义

回归测试：修改后，重新检查原来能工作的行为有没有退步。

相关：根据改动可能影响的范围选择测试。拆插入模块要检查目标选择、粘贴和剪贴板；纯界面改动主要检查布局和按钮状态，通常无需重跑云端模型样本。涉及整条录音链路，则补一条完整流程检查。

自动化能验证程序逻辑；真实麦克风、系统权限、应用焦点和云端识别效果仍有实机边界。两种证据分别记录，不互相冒充。
