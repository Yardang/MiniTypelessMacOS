# 功能变更与交付流程

PRD 说明“产品应该怎样工作”；变更记录说明“为何改、改了什么”；测试证明“哪些行为已经验证”；Git 提交保存“具体代码版本”。四者相互链接，不能互相代替。

## 每次功能变更必须遵循

1. **核实基线**：读 PRD、相关变更记录、源码与 Git 状态；区分正在运行、已安装、工作区三个版本；保留可用旧版和密钥。
2. **明确需求**：说明用户问题、预期行为、例外情况、数据去留。对睡眠/取消/重试/自动发送等影响行为的问题先澄清；未知项不能默认为用户同意。可提出不同意见并解释理由。
3. **先更新文档**：在 PRD 分配/复用 MT-* 编号；建立 docs/changes/CHG-YYYYMMDD-NN.md，写范围、取舍、受影响模块、验收条件。未完成状态明确写“待实现”。
4. **小范围实现**：按职责改动，避免顺手改模型、密钥、界面和其他无关流程。保留异常路径、取消隔离和旧结果处理。
5. **验证**：先复现旧缺陷或写能区分旧/新行为的测试，再运行相关回归。共享生命周期改动运行全套离线回归与 Debug/Release 编译；实际硬件/权限/系统睡眠另列实测边界。不反复要求用户重测未受影响场景。
6. **审阅与交付**：检查差异、需求—测试对应、敏感信息、签名身份、安装文件指纹；独立安装，未经当前授权不退出用户正在使用的程序。记录可回退版本。
7. **完成记录**：同步 PRD、README、CHANGELOG、变更记录；以本地 Git 提交记录已验证工作，勿将无关用户改动混入。历史积压先列明来源；如果暂未提交必须明确原因。未经授权不推送或发布。

## 完成标准

需求明确 + 实现完成 + 对应自动测试通过 + 文档一致 + 构建可追溯。仍需实机验收时写“开发完成，实机待验”，不能标成全部验收通过。发现新问题只更新关联条目，不随意改写历史通过结论。

## 初学者说明

“回归测试”是检查修改有没有让原来正常的功能退步。“验收条件”应具体可观察，例如“重复收到两次唤醒通知只发出一次转写请求”，而非“睡眠功能正常”。“基线”是本次修改前可对照、可恢复的版本。
