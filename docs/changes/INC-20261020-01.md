# INC-20261020-01 — 转写请求连续连接中断

状态：已定位到当前代理连接路径，具体代理组件/节点原因尚未确定；实际录音恢复待验证。关联：MT-REC-001、MT-ERR-001、MT-OBS-001。基线：2c202bf，诊断版本 2026-10-20-standby-1。本轮没有功能变更。

## 证据

应用日志（America/New_York，10 月 20 日）显示 23:34:57、23:41:28、23:45:01、23:45:48 的首次转写及 23:46:05 的手动重试均在约 5 秒后以 network / -1005 失败。对应录音约 112.35、0.73、2.46、17.47 秒（最后一段重试）。均有录音开始、停止及转写事件；未进入整理/插入。不能将这组故障描述为 Fn 没响应或录音时长超限。

更早 10:39 的 noSpeech 是另一种错误，不与本次网络失败合并归因。此前确有多次成功处理；本次不撤销已完成的功能验证结论。

## 无密钥、无音频连接对照

所有探测只向既有百炼地址发送空 JSON，不携带 Authorization，不上传用户音频，不改系统网络设置：

| 路径 | 结果 |
| --- | --- |
| curl 常规路径（无代理环境变量、不显式采用系统 HTTP 代理）→ ASR | HTTP 401，TLS 校验通过，约 0.60 秒 |
| 同路径 → 文字接口 | HTTP 400，约 0.46 秒 |
| 独立 Swift 进程 URLSession.shared，与应用相同方式 → ASR | 系统码 -1005，约 5.10 秒 |
| curl 显式使用当前系统 HTTPS 代理 → ASR | curl 56，无 HTTP 响应，约 5.10 秒 |

系统 HTTP/HTTPS 代理开关均启用；不记录代理地址、端口、完整网络响应或用户内容。空请求的 401/400 是无凭据/无有效请求体条件下的响应，只证明服务可达，不验证真实模型请求或账户有效性。

对照支持故障集中在当前代理路径；不能仅凭这些结果进一步断言代理软件、节点、上游网络或服务端针对该出口的行为谁负主要责任。新建 URLSession 进程也失败，不支持仅重启 App 即可修复的结论。

[Apple 对 -1005 的定义](https://developer.apple.com/library/archive/qa/qa1941/_index.html)：请求进行中承载连接中断；POST 不能据此判断远端是否已处理，因此沿用手动重试、可能重复计费的提示，不擅自加入自动重发。

## 恢复与验收

先另存需要的待重试录音；成功开始下一段会按已确认规则替换它。建议在用户使用的代理软件中将 `dashscope.aliyuncs.com` 设为直连，或切换可正常访问该服务的线路；不擅自关闭全局代理或在应用中隐式绕过用户网络策略。调整后先做同路径空请求检查，再由用户点击一次“重试转写（重新上传）”。

验收：转写/整理成功，结果可复制；既有手动重试策略不自动插入，需要用户复制或手动插入。实际语音请求尚未验证恢复，不能把无凭据探测当作完整业务通过。

本轮仅排查并记录证据，没有修改生产代码、重启应用或读取密钥；无需重跑不受影响的离线功能测试。
